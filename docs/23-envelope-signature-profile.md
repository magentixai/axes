# Envelope Signature Profile: `axes:envelope_signature_ed25519@1`

> **Status: normative profile (D-060), published for challenge, with two-sided vectors.** The gt-v2.1 corpus still carries stub signatures marked `stubbed`; the first corpus release with real signatures is the next one (see section 6).

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119 and RFC 8174.

## 1. What a signature adds

The envelope hash and chain show that bytes have not changed since they were committed to. They do not show who committed to them: anyone holding the bytes can recompute a hash. A signature over the envelope hash, with a key the emitter controls, adds that. It still says nothing about whether capture was complete, which is what sequence, heartbeat and anchoring evidence are for.

## 2. Members (inside `integrity`)

| Member | Inside the hash | Meaning |
|---|---|---|
| `signing_key_id` | yes | The key that signed. Already present in every corpus envelope |
| `signing_key_provenance_ref` | yes | Where the key's custody is described (for example a KMS record). Optional |
| `envelope_signature_profile_ref` | yes | `axes:envelope_signature_ed25519@1` for this profile |
| `envelope_signature_basis_status` | yes | `demonstrated` when the producing tool made a real signature under this profile; `stubbed` otherwise. Written by the tool, never by hand |
| `envelope_signature` | no (`self_referential`, docs/09a) | The signature, base64url without padding (RFC 4648 section 5) |

Because the profile reference, the key identity and the basis status are inside the hash, a signature cannot be moved to a different key or profile without breaking the envelope hash.

## 3. Signing

1. Complete the envelope, including the members in section 2 except `envelope_hash` and `envelope_signature`.
2. Compute the envelope hash as docs/09 specifies.
3. Build the signing input: the RFC 8785 bytes of

   ```json
   {"domain_tag": "axes:envelope_signature@1", "envelope_hash": "<hex>", "hash_algorithm": "SHA-256", "se_version": "0.1-draft"}
   ```

   with the envelope's own `hash_algorithm` and `se_version`. The domain tag keeps a signature made for AXES from being replayed into another protocol built on the same canonical form, and the reverse (D-050).
4. Sign the signing input with Ed25519 (RFC 8032, pure Ed25519, no context, no prehash) and store the 64-byte signature in `envelope_signature`.

Signing keys SHOULD be held outside the emitter process (KMS or HSM), so that a compromised emitter cannot sign history it did not produce.

## 4. Verifying

A verifier recomputes the envelope hash from the bytes, never using the declared `envelope_hash`, builds the signing input, resolves the public key and checks the signature. Results, in the four-state vocabulary (docs/06):

| Situation | State | Reason | Condition | Subject |
|---|---|---|---|---|
| Signature verifies | `verified` | | | `artifact` |
| `envelope_signature_basis_status` is not `demonstrated` | `indeterminate` | `absence` | `basis_not_demonstrated` | `operator` |
| A profile the verifier does not implement | `not_evaluated` | `instrument_failure` | `signature_profile_unsupported` | `verifier` |
| `signing_key_id` not in the verifier's signing key set, or not an Ed25519 key | `indeterminate` | `absence` | `signing_key_unresolved` | `operator` |
| Signature does not verify, or is not valid base64url of 64 bytes | `contradicted` | `divergence` | `envelope_signature_invalid` | `artifact` |
| Declared hash or canonicalisation not implemented | `not_evaluated` | `instrument_failure` | `hash_algorithm_unsupported` | `verifier` |

A content change after signing shows as `envelope_signature_invalid` even if the forger recomputed `envelope_hash`, because the signing input uses the recomputed hash.

## 5. Signing key sets

Public keys reach verifiers in a signing key set: a JSON document with `signing_key_set_id` and `signing_keys[]`, each entry carrying `signing_key_id`, `public_key_algorithm` (`Ed25519`) and `public_key_value` (the 32-byte public key, base64url without padding). In a bundle the key set is a file listed in the manifest, so its digest is committed with the evidence. How a relying party decides to trust a key set (pinning, a directory, a certificate) is outside this profile.

## 6. Vectors and the next corpus release

- `vectors/signatures/`, generated by `tools/generate_signature_vectors.py`, has seven two-sided cases: a valid signature, content changed after signing, one signature bit changed, a value that is not base64url, an unresolved key, an unsupported profile, and a stub as in gt-v2.1. The key is RFC 8032 section 7.1 TEST 1, whose secret is published: these vectors prove the construction, not an identity.
- `tools/axes_ed25519.py` is RFC 8032's reference algorithm in the standard library, checked against RFC 8032 tests 1 to 3. An independent check with Go's `crypto/ed25519` agrees with every vector.
- The gt-v2.1 corpus is frozen and keeps its stub signatures. The next corpus release carries real signatures under this profile, together with `sequence_stream_id`, top-level `idempotency_key` and `execution_reality_mode` (D-052, D-055, D-057). Until then, signature verification of the corpus correctly reports `basis_not_demonstrated`.

## 7. Open points (challenge welcome)

1. A COSE or JWS encoding of the same signing input, for ecosystems that require one.
2. Key rotation within a stream, and validity periods in the key set.
3. Recipient countersignatures over `recorded_at` (docs/09a option D) as a second signature under a related profile.
